# 8.8 Configuration, environments and secrets \{#8-8-configuration-environments-and-secrets\}

**Three environments**

| Environment | Purpose | Environment name |
| --- | --- | --- |
| Development | Developer machine | `Development` |
| SIT | System integration testing, for testers after deployment | `SIT` |
| Production | Live | `Production` |

- The Api uses `ASPNETCORE_ENVIRONMENT` and the Worker uses `DOTNET_ENVIRONMENT` to set the environment name.
- When unset, .NET defaults to `Production`, so a missing variable applies the strictest settings rather than exposing development features.
- Local development sets `Development` through `launchSettings.json`; nothing to set by hand.
- The environment name must match the settings file name **exactly, including case**. Linux file systems are case sensitive, so an environment named `Sit` will not find `appsettings.SIT.json`.

**Settings file layering**

The Api and the Worker each have four settings files. .NET loads the base file first, then overrides it with the environment file:

1. `appsettings.json`: the base file, holding the structure shared by all environments and **the safest defaults** (all features off, connection strings empty).
2. `appsettings.Development.json`: local Docker connection strings, OpenAPI and startup migrations on, more detailed logging.
3. `appsettings.SIT.json`: OpenAPI on for testers, everything else the same as production.
4. `appsettings.Production.json`: only what production changes relative to the base file.

See [16.12](../../code/16-api.mdx#16-12-appsettings-files-4) and [17.1](../../code/17-worker-optional.mdx#17-1-appsettings-files-4) for each file's content.

**Differences by environment**

| Setting | Development | SIT | Production |
| --- | --- | --- | --- |
| Connection strings | Settings file (local Docker defaults) | Environment variables or a secrets manager | Environment variables or a secrets manager |
| MediatR license key | User Secrets | Environment variables or a secrets manager | Environment variables or a secrets manager |
| Authentication Authority and Audience | Settings file or User Secrets | Environment variables | Environment variables |
| OpenAPI and Scalar | On | On | Off |
| Automatic migrations at startup | On | Off (same process as production) | Off |
| Seq URL and API key | Settings file (local Docker) | Environment variables | Environment variables |
| Log output | Console + local Seq | Console (Warning and above) + local JSON files + Seq | Same as SIT |
| Log file retention | No files | 14 days | 30 days |
| Log level | Debug | Information | Information |
| CORS | Local frontend URL | SIT frontend URL | Production frontend URL |

**Principles**

- Apart from OpenAPI, SIT is **kept as close to production as possible**, including migration method and log format, so the deployment process is rehearsed on SIT first.
- Toggle style features (OpenAPI, startup migrations) are driven by settings, never by checking the environment name in code; a new environment needs only a new settings file.
- **Arrays in settings files merge by index across files**; they are not replaced wholesale. So Serilog's `WriteTo` uses **named objects** (`Console`, `File`, `Seq`) instead of an array, defined only in the environment files; there is also no `Using` block, since Serilog loads referenced packages automatically. Named objects also let an environment variable override a single setting, for example `Serilog__WriteTo__Seq__Args__serverUrl`.

**Secrets**

- Settings files hold **only non secret** values. SIT and production passwords, license keys and other secrets **must never be committed**; the local Docker default credentials are not secrets and can live in `appsettings.Development.json` so local development works out of the box.
- Local development stores secrets with .NET User Secrets (`dotnet user-secrets set "key" "value"`).
- SIT and production use environment variables or a cloud secrets manager (such as Azure Key Vault or AWS Secrets Manager). Environment variables use a double underscore for nesting, for example `ConnectionStrings__Database`.
- SIT and production must use **different** databases, brokers and secrets; nothing is shared.
- The MassTransit v9 license is read from the environment: `MT_LICENSE` holds the license text, or `MT_LICENSE_PATH` points to the license file. Locally, keep the file outside the repository and export `MT_LICENSE_PATH` in your shell profile; on the VMs set `MT_LICENSE` in the env files (12.9); in CI use the `MT_LICENSE` secret (12.10). It is never committed. Without it the Api, the Worker and the integration tests fail at startup.
