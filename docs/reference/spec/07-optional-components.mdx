# 7. Add-ons \{#7-optional-components\}

The core Skeleton Solution is Clean Architecture, DDD and CQRS with no database, broker or sign in: it builds, runs and tests on its own. Everything else is an **add-on**, added after the core runs and only when the project needs it. In Part 2, the files and lines that belong to an add-on are marked "(add-on: X)"; [11.4](../code/11-file-overview.mdx#11-4-core-and-add-on-files) lists them.

| Add-on | Requires | When needed | Section |
| --- | --- | --- | --- |
| PostgreSQL | Nothing | The system stores data; almost every backend | [7.4](#7-4-postgresql) |
| Messaging | PostgreSQL | Integration events to other systems or to the Worker | [7.5](#7-5-messaging), [7.2](#7-2-outbox-and-the-worker) |
| Worker | Messaging | Consumers, scheduled jobs or long running work | [7.1](#7-1-worker) |
| Auditing | PostgreSQL | You need to trace who changed what and when | [7.3](#7-3-audit-records) |
| Authentication | Nothing | Users or systems must sign in | [7.6](#7-6-authentication) |
| Go live | Nothing | Deploying to SIT and Production | [7.7](#7-7-go-live) |

Add them in this order. Each one is a few new files plus a few highlighted lines in existing ones, so it is easiest to add before features depend on the core's shape. The Setup Flow's Add-ons pages walk through each one; the prompts below do the same with an AI coding agent.

## 7.1 Worker \{#7-1-worker\}

**When to add**: the project has work that runs in the background and is not triggered directly by a user action, for example consuming async messages, running scheduled jobs or processing long batches. It requires the Messaging add-on. With a Worker, the Worker delivers the Outbox; without one, the Api delivers it (see [7.2](#7-2-outbox-and-the-worker)).

**Why it is separate from the Api**:

- The Api should respond quickly and finish; background work runs long and needs retries.
- Inside the Api it would slow requests, and an Api restart would interrupt it.
- Separated, each can be deployed, scaled and restarted independently.

**How it works with the Api**:

- When the Api receives a request that needs lengthy processing, it only records and publishes a message, then returns at once; the Worker does the real work.
- The Worker holds no business logic. Like the Api it is only an entry point, and both end up calling Application Commands.
- A project that needs scheduled jobs but no broker is not covered by the template: add a `BackgroundService` to the Api, or add Messaging first.

## 7.2 Outbox and the Worker \{#7-2-outbox-and-the-worker\}

The Outbox is not a separate switch; it comes with the Messaging add-on, configured with MassTransit. It uses MassTransit's built in EF Core Transactional Outbox rather than a custom one: published messages are written to the Outbox table in the same transaction as the business data, then a delivery service sends them to the broker. See [8.4](./08-design-rules/04-masstransit-async-messaging.mdx).

- **With a Worker**: the Api only writes to the Outbox and disables its delivery service; the Worker delivers.
- **Without a Worker**: the Api delivers; just remove the check in [15.8](../code/15-infrastructure.mdx#15-8-dependencyinjection-cs) that disables the delivery service.

The English guide's appendix proposes a custom `OutboxMessage` table polled by Quartz.NET. This template does not use it; see [Appendix B](../appendix/b-decision-record.mdx) for why.

## 7.3 Audit records \{#7-3-audit-records\}

**When to add**: any project that must trace "who changed which record, when, and from where". Most real business systems need this, so **add it before the first feature**. It requires the PostgreSQL add-on.

**Why it belongs in the template**: audit records only accumulate from the moment they are enabled. Adding them after go live means the earlier change history can never be recovered. The template provides only the generic mechanism; **each project decides what to audit**, and the template contains no business content.

**Three levels**

| Level | What it records | How it is produced | Provided by the template |
| --- | --- | --- | --- |
| Data change audit | Entity inserts, updates and deletes, with old and new values of changed columns | EF Core interceptor, automatically | Yes |
| Operation audit | Who ran which Command or Query, including failed attempts | MediatR pipeline, only for marked requests | Yes |
| Security events | Sign in, sign out, password and permission changes | Identity provider | No, the provider records them |

**Data change audit (`AuditTrails` table)**

- Only entities that implement the marker interface `IAuditable` are audited; others are not recorded.
- On each `SaveChangesAsync`, the interceptor creates one record per change to an audited entity and **writes it in the same transaction** as the business data: if the data is saved, the audit record exists; if the save fails, neither is written. Application logs cannot guarantee this.
- Inserts record every column's value; updates record only the old and new values of changed columns; deletes record the values before deletion.
- Sensitive columns (such as password hashes or tokens) are excluded with `[AuditIgnore]`; `CreatedAt` and `UpdatedAt` are excluded automatically.
- Prerequisite: entity IDs are generated by the domain (see [8.13](./08-design-rules/13-strongly-typed-ids.mdx)), so an ID exists at insert time.
- Limitation: currently plain properties are recorded. Value objects mapped as EF Core Complex Types need extra handling in the interceptor; those mapped as Owned Types must also implement `IAuditable`.

**Operation audit (`OperationAudits` table)**

- Only Commands or Queries that implement the marker interface `IAuditableRequest` are recorded. Use it for important operations and for Queries that read or export sensitive data.
- Records the request name, outcome (success, business failure, exception), error code and the shared information below.
- The pipeline sits before validation, so **failed validation attempts are recorded too**.
- It writes through a separate DbContext, so a failed request's unsaved changes are never written along with it.
- If writing the operation audit fails, an Error log is written but the request result is unchanged (data integrity is already guaranteed by the data change audit).
- Request bodies are not recorded, to keep sensitive data out of the audit tables.

**Information shared by both records**

`UserId`, `SessionId` (the token's `sid` claim), `ClientIp`, `UserAgent` (device and browser), `TraceId` (cross references application logs) and the time. `IAuditContext` supplies them; in the Worker there is no HTTP request, so `UserId` and similar fields are empty, meaning the system performed the action.

**Protection and retention**

- Audit tables are **insert only**: the database account the application runs with has only `INSERT` and `SELECT` on them and cannot update or delete (see [8.11](./08-design-rules/11-database-migrations.mdx)).
- Retention follows the regulations or contracts that apply to the project and is not preset in the template; with large volumes, partition by month and move old data to archive storage.
- Audit records and application logs are fully separate: logs are for troubleshooting and may be deleted after their retention period; audit records are business data and must be kept long term.

Its files are the ones in sections [13](../code/13-domain.mdx) to [15](../code/15-infrastructure.mdx) marked "(add-on: Auditing)", plus the related DI registrations.

## 7.4 PostgreSQL \{#7-4-postgresql\}

**When to add**: the system stores data, which is almost always. Add it first: Messaging and Auditing build on it.

**What it adds**: EF Core with Npgsql ([15.1](../code/15-infrastructure.mdx#15-1-applicationdbcontext-cs) to [15.4](../code/15-infrastructure.mdx#15-4-repository-cs)); `IApplicationDbContext` and `IUnitOfWork` in Application ([14.10](../code/14-application.mdx#14-10-iapplicationdbcontext-cs), [14.11](../code/14-application.mdx#14-11-iunitofwork-cs)); migrations, applied at startup in Development and by a migration bundle elsewhere ([8.11](./08-design-rules/11-database-migrations.mdx)); the database health check; optimistic concurrency ([8.17](./08-design-rules/17-concurrency-control.mdx)); and a PostgreSQL container for the integration tests.

**Domain events before and after.** Aggregates raise domain events in the core too, and the Domain tests check them (`AssertDomainEventWasPublished`, [18.2](../code/18-tests.mdx#18-2-basetest-cs-domain-unittests)). Nothing dispatches them until there is a unit of work: with this add-on, `ApplicationDbContext.SaveChangesAsync` publishes them through MediatR before writing, so their handlers' changes commit in the same transaction ([15.1](../code/15-infrastructure.mdx#15-1-applicationdbcontext-cs)).

## 7.5 Messaging \{#7-5-messaging\}

**When to add**: the system tells other systems, or its own Worker, that something happened. It requires PostgreSQL, because the Outbox and Inbox are tables in the same database as the business data.

**What it adds**: MassTransit v9 with RabbitMQ, the EF Core Transactional Outbox and an Inbox on every Consumer ([7.2](#7-2-outbox-and-the-worker), [8.4](./08-design-rules/04-masstransit-async-messaging.mdx)); `IEventBus` in Application ([14.7](../code/14-application.mdx#14-7-ieventbus-cs)); RabbitMQ in Docker Compose and in the integration tests. MassTransit v9 needs a license ([8.5](./08-design-rules/05-third-party-licensing.mdx), [8.8](./08-design-rules/08-configuration-environments-and-secrets.mdx)).

## 7.6 Authentication \{#7-6-authentication\}

**When to add**: users or other systems must sign in. Without it, every endpoint is public.

**What it adds**: JWT Bearer validation against any OpenID Connect provider, a fallback policy that requires sign in everywhere, permission checks per endpoint, `ICurrentUser` and `IPermissionProvider` ([8.16](./08-design-rules/16-authentication-and-authorization.mdx), [16.7](../code/16-api.mdx#16-7-authextensions-cs) to [16.10](../code/16-api.mdx#16-10-permissionendpointextensions-cs)).

## 7.7 Go live \{#7-7-go-live\}

**When to add**: the project is ready for SIT and Production. Add it last: its files include only what the other add-ons need.

**What it adds**: the systemd, Nginx and environment templates under `deploy/` and the CI workflow ([12.7](../code/12-solution-level.mdx#12-7-deploy-systemd-service-files) to [12.10](../code/12-solution-level.mdx#12-10-github-workflows-ci-yml)), and the deployment process of [8.21](./08-design-rules/21-deployment.mdx). Without the Authentication add-on, every endpoint will be public: confirm that is intended.
